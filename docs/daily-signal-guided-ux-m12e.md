# M12-E 日线信号策略引导式配置

M12-E 只调整配置、预检和补齐导航体验。数据库 Schema 保持 17；策略参数、指标公式、
信号日期、下一交易日开盘执行、成交、费用及历史结果语义均未改变。

## 页面流程

页面按“研究范围、候选股票、买入条件、卖出条件、检查并运行”组织，并提供简洁/高级显示。
模式切换只展开或收起低频设置，不修改参数。底部操作栏始终说明按钮为什么可用或不可用：

1. 读取所选股票池的准确 revision 和冻结成员；读取完成前不显示虚假的 0 只。
2. 就近检查候选数量、最大持仓、日期和买卖规则。
3. 用户点击“检查本地数据”后，后端只读预检。
4. 页面把多只股票、多个口径产生的原始检查按根因归并为问题卡片，同时保留完整明细。
5. 参数或范围一旦变化，原预检立即失效，必须重新检查。
6. 只有预检通过后才能进入提交前核对；最终确认后才提交回测。

## 快捷修正

快捷按钮只填写用户可见且可验证的建议值，不会自动提交：

- 候选数量大于冻结范围：可明确改为冻结股票数量。
- 最大持仓大于候选数量：可明确改为当前候选数量。
- 结束日期超过最新完整交易日：采用后端返回的完整日期。
- 开始日期早于股票上市日：采用后端返回的最晚相关上市日期。

每次快捷修正都会使旧预检和旧补齐确认失效。候选样本不足、财务缺失等无法安全自动决定的
问题只提供定位和解释，不擅自改变策略。

## 预检问题与原始检查

后端 recommendation 保留原 `code/title/explanation/action`，并向后兼容地追加 `field`、
`suggested_value`、`action_kind`、`affected_symbols` 及
`network_required_for_resolution` 等展示提示。前端按稳定 code 去重，不解析中文字符串。

首层显示“问题类别数”，例如 5 类问题；“23 项原始检查未通过”仍可展开核对。未知问题不被
隐藏，原始 checks、blockers、warnings 和内部代码保持不变。

## 数据页往返

创建补齐计划后，计划 ID 就是冻结草稿身份。前往“数据与股票池”时携带计划 ID 和只允许站内
日线策略地址的 `return_to`。数据页只读取该计划并显示返回入口；返回后重新读取原冻结参数，
必要时只读地重新预检。浏览、返回和重新预检都不会自动联网、补齐或运行回测。

## 已确认补齐任务的后台恢复

M12-E.1 修复了已确认计划长期停在 `queued · 0%` 的调度问题。共享的有界调度器不再硬编码
管理股票任务，而由每个实例声明自己可以领取的数据集：管理股票实例只领取
`managed_stock` 和 `managed_stock_gap_verification`，研究补齐实例只领取
`research_data_plan`。确认接口会立即尝试调度，服务启动后的五秒有界轮询也会恢复数据库中原有的
等待任务。

恢复不会重新创建任务，不改变计划 ID、版本、参数哈希或冻结范围。任务仍使用原有 owner、
heartbeat、fencing 和 `.managed-download.lock`；下载槽暂时繁忙时保持等待并在后续轮询重试。
失败任务仍需用户明确重试，成功任务不会重新执行，完成补齐后只重新预检而不会自动运行策略。

## 错误位置与无障碍

- 字段错误显示在字段或所属配置区旁，并设置 `aria-invalid`/`aria-describedby`。
- 点击预检、提交或补齐后产生的错误显示在相应按钮附近，并进入键盘焦点和可视区域。
- 后台轮询失败只更新任务区域，不抢夺滚动位置或焦点。
- 页面支持点击、键盘和触摸；`prefers-reduced-motion` 下取消平滑滚动动画。
- 390px 下操作按钮单列，问题卡片和长说明换行；长表格仍只在局部横向滚动。

## 行情发布后的交易日缺口核验

M12-E.2 把“下载行情”和“解释无行情日期”拆成两个需要分别确认的步骤。研究补齐项目已经
`published` 后，如果交易所开市日仍没有 none/qfq K 线，计划保留原来的
`completed_with_gaps` 结果，并在日线策略页显示独立的“交易日缺口核验”区域。查看日期、
证据和打开确认框均为只读；只有用户最终确认后，才复用既有
`managed_stock_gap_verification` 任务访问停牌或交易状态来源。

核验请求冻结原计划 ID、版本、参数哈希、股票池 ID/revision、股票代码范围哈希、管理股票
revision 和最多 100 个精确日期。研究补齐调度器仍只领取 `research_data_plan`；核验任务只由
允许 `managed_stock_gap_verification` 的管理股票调度器领取。核验不会重新下载已发布行情，
不会生成 K 线、填零或复制前收，也不会运行策略。

页面按 M12-D.2 的四类结果展示：

- `verified_suspension`：有可靠停牌证据，可作为合理无行情；不生成虚假 K 线。
- `missing_bar`：应有行情但本地缺失，继续阻断并需要另行精确补齐。
- `calendar_mismatch`：交易日历冲突，继续阻断且不能靠重下个股行情解决。
- `unverified_gap`：证据不足或查询失败，继续保守阻断，可由用户明确重试核验。

核验任务达到终态后，页面对原冻结参数自动执行一次只读预检。只有最新预检真正通过才启用
“核对并运行”，自动预检绝不会提交回测。参数或范围已变化时，旧任务结果只保留在历史中，
不会覆盖当前页面。补齐项目表、缺口证据和补齐任务结束时的预检报告使用三个独立容器；长日期
和错误只在局部换行或滚动，状态刷新还会恢复用户已展开的明细。

## 服务器人工验收

1. 选择一个 11 只股票的历史 revision，确认读取期间显示“正在读取”，随后显示准确 11 只，
   不出现“冻结范围只有 0 只”。
2. 将候选数量设为 20，确认错误出现在候选区；点击“改为 11 只”，确认只修改字段并要求重新预检。
3. 将最大持仓设为大于候选数量，确认成本与执行区附近出现修正按钮。
4. 选择短周期不小于长周期，确认错误位于对应买入/卖出区；点击摘要中的错误可回到该区。
5. 选择未来结束日期并预检，确认问题卡片显示后端建议日期；采用后不会自动预检或运行。
6. 构造多股票 none/qfq 缺口，确认首层按根因归并，完整原始检查仍可展开。
7. 创建补齐计划，前往数据页再返回，确认计划 ID、股票池 revision、冻结范围和参数均保留。
8. 确认浏览、模板、快捷修正、预检和返回均没有创建下载任务或回测任务。
9. 在 390px、768px、1440px 检查进度条、字段错误、问题卡片和底部操作栏。
10. 确认补齐计划后，任务应从“等待执行”进入实际处理；刷新或关闭页面不影响后台任务。
11. 在任务仍为 `queued` 时重启 Web 服务，确认原 task ID 自动恢复执行，且无需再次确认。
12. 同时存在管理股票和研究补齐任务时，确认两个调度器只领取各自的数据集，不串任务。
13. 构造 none/qfq 共同缺口，确认补齐完成后出现独立的“确认核验缺失日期”，并显示前 20 个
    日期、四类数量、证据来源和最近核验时间。
14. 打开核验确认框，确认包含计划 ID、参数哈希、冻结范围哈希、股票数和日期数；取消后没有
    创建任务或联网。
15. 确认核验后，确认任务归属 `managed_stock_gap_verification`，原 `published` 行情项目不被
    改写或重复下载；任务结束后自动重新预检，但不自动运行回测。

## 已知限制

候选财务样本在历史时点不足时，系统不能仅凭当前汇总确定一个安全的新候选数量，因此不会提供
可能改变研究意图的一键修正。数据页返回依赖仍然存在的补齐计划；计划被删除或与页面类型不兼容
时会明确提示恢复失败。
